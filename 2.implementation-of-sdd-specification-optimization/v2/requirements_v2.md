# 工廠維修工單管理系統 v2.0 延伸需求文件（PRD）

---

## 背景說明

v1.0 系統已成功建立了工廠維修工單的數位化基礎：報修、追蹤、摘要、搜尋一應俱全，現場人員的回報流程也因 Wizard 模式而明顯改善。然而，在實際產線導入試用後，廠務管理層提出了幾點觀察：

第一，目前系統對「設備」本身沒有記憶——同一台機器反覆出現相同故障，系統卻無法識別這是慣性問題還是偶發事件。每次開工單都是一張白紙，管理者必須自行翻查歷史才能判斷是否為重複故障，這讓 `recommend` 的建議可信度受到質疑。

第二，`summary` 指令提供的是全局靜態數據，但生管人員更關心的是「**這週**比**上週**多了幾張工單」、「**L2 產線**本月累積停機幾小時」這類帶有時間與範圍條件的查詢，目前系統無法滿足。

第三，工單結案後缺乏標準化的結案資訊，「closed」只代表問題消失了，但沒有記錄**用什麼方法解決的**、**實際花了多少時間**。這讓維修知識無法沉澱，下次遇到相同問題仍需從零開始診斷。

基於以上回饋，v2.0 將在不破壞現有指令介面的前提下，針對上述三個痛點進行延伸開發。

## 需求列表

### 需求一｜強化結案流程，補齊工單生命週期（修改既有模組）

目前 `update --status closed` 只是單純修改狀態欄位。客戶希望將「結案」視為一個獨立的業務動作，而非普通的欄位更新。

**具體期望行為如下：**

- 當一張工單被標記為 `closed` 時，系統應額外要求填寫兩項資訊：**實際維修耗時（分鐘）** 與 **結案處置描述**（例如「更換 #3 軸承，廠商料號 BRG-2048」）。
- 這兩項資訊在結案時為**必填**——若未提供，系統應拒絕執行並給予提示，而非靜默忽略。
- 結案後的工單在 `show` 指令中應能明顯呈現這些結案資訊，與一般的 `note` 備註有所區隔。

> **設計空間**：這項需求涉及既有 `update` 指令的行為改變，以及 Ticket 資料模型的調整。如何在不破壞 `update` 現有其他參數功能的前提下，優雅地加入這個「結案動作」，請自行設計。是否需要新增獨立的 `close` 指令，或在 `wizard` 中加入結案引導路徑，皆可自行評估。

---

### 需求二｜設備健康度追蹤，識別高故障率機台（全新功能）

廠務管理員希望系統能自動彙整**以設備為單位**的歷史維修紀錄，用來識別哪些機台是「慣性故障機」。

**具體期望行為如下：**

- 新增一個 `machine` 指令（或類似名稱），輸入設備 ID 後，能顯示該設備的彙整資訊，至少包含：歷史工單總數、各狀態工單數量、累積停機總時間、最常出現的故障類型。
- 在 `recommend` 指令的評分邏輯中，應將設備的歷史故障頻率納入考量——一台過去三個月內開過五張工單的機器，其建議優先序應高於同優先級但歷史清白的機台。目前的評分公式僅考慮 `priority` 與 `downtime_minutes`，這顯然不夠。
- 如何定義「歷史故障頻率」的計算方式（例如：總工單數、近 N 張工單的時間密度、或其他指標），請自行設計並在 SDD 中說明你的選擇理由。

> **設計空間**：此需求不要求建立獨立的設備資料表或新增 JSON 結構，可從現有工單資料中動態彙整。但若你認為有必要調整資料模型，也請說明你的設計決策。

---

### 需求三｜帶條件的統計查詢，讓 `summary` 更具生管價值（修改既有模組）

目前 `summary` 總是輸出全量資料的統計，無法縮小範圍。

**具體期望行為如下：**

- `summary` 應支援至少兩種過濾維度：**時間區間**（例如：指定起始日期與結束日期）與**產線別**（`--line_id`）。
- 當指定過濾條件時，統計數字應只反映符合條件的工單，並在輸出面板的標題或說明中清楚標示當前的查詢條件（例如：「L2 產線 ｜ 2025-01-01 至 2025-03-31」）。
- 無任何條件時，行為與 v1.0 相同（維持向下相容）。

> **設計空間**：日期格式的輸入規格、不合法日期範圍的錯誤處理方式，請自行定義並寫入 SDD。

---

### 需求四｜工單匯出功能，支援離線存檔與跨系統對接（全新功能）

廠務主管每月需向上級提交維修報告，目前只能對著終端機截圖，格式難以整理。

**具體期望行為如下：**

- 新增 `export` 指令，能將工單資料輸出為 **CSV 格式**的檔案，預設儲存於執行目錄，檔名應包含匯出時間戳記（例如 `tickets_export_20250601_1430.csv`）。
- `export` 應支援與 `list` 相同的過濾邏輯（至少支援 `--status` 與 `--line_id`），讓使用者可以只匯出特定範圍的資料。
- 匯出完成後，終端機應顯示成功訊息與實際儲存的檔案路徑，以及本次匯出的工單筆數。

> **設計空間**：CSV 的欄位順序與 `note` 備註的呈現方式（備註有多筆，但 CSV 是扁平結構）請自行設計，並說明你的處理決策。

## 驗收標準

以下以使用者可觀察的行為描述驗收條件，不限定實作方式：

| # | 驗收情境 | 可觀察的預期行為 |
|---|----------|-----------------|
| A | 嘗試將工單結案但**未提供**結案描述 | 系統拒絕操作，輸出明確提示說明缺少哪些必填資訊，工單狀態維持不變 |
| B | 正常完成結案流程（含耗時與描述） | `show` 該工單時，結案資訊以有別於一般備註的方式顯示，且不可被後續 `note` 指令覆蓋 |
| C | 查詢一台有三張以上歷史工單的設備 | 輸出包含各狀態工單數、累積停機時間、最常見故障類型，資訊正確無誤 |
| D | 執行 `recommend`，其中一台設備有大量歷史工單 | 該設備的工單排序明顯受歷史頻率影響，Score 欄位數值可反映此加權 |
| E | 執行帶 `--line_id L2` 的 `summary` | 面板標題或說明文字標示「L2 產線」，統計數字不包含其他產線工單 |
| F | 執行帶日期範圍的 `summary`，但結束日期早於起始日期 | 系統輸出錯誤提示，不執行統計，退出碼非 0 |
| G | 執行 `export --status open` | 目錄下出現帶時間戳記的 CSV 檔，內容僅含 `open` 工單，終端顯示檔案路徑與筆數 |
| H | 執行 `export` 但無任何符合條件的工單 | 系統提示無符合條件的資料，**不產生空白 CSV 檔案** |
